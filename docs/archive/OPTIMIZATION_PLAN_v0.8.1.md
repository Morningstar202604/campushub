# CampusHub 优化方案：前端 + 后端 + 使用者视角

> 基线：`gitcode.com/badhope/campushub` v0.8.1（commit 基线 `00277c2` 之上的变更）
> 日期：2026-09-16
> 范围：前端体验重构、后端逻辑增强、按使用者角色重排优先级

---

## 一、先说结论：之前交付的原型有 4 处硬伤

我对照源码逐文件核对后，发现上一版原型与真实项目存在结构性偏差：

| # | 项目 | 真实源码 | 旧原型 | 性质 |
|---|------|---------|--------|------|
| 1 | tabBar | 首页 / **二手** / **指南** / 我的 | 首页/二手/失物/表白墙/我的 | 入口结构错误 |
| 2 | 首页版式 | **双列瀑布流**（`leftList`/`rightList` 分列渲染） | 单列卡片流 | 信息密度减半 |
| 3 | 首页 tab | 推荐 / **热门** / 最新 | 推荐/二手/失物/表白 | 与分类筛选混淆 |
| 4 | 主题色 | `#4A90D9`（`app.json` 的 `selectedColor`） | `#07C160` 微信绿 | 品牌色错误 |

此外，失物招领与表白墙**不是 tabBar 页**，而是从首页顶栏 `🎒失物` / `💌墙` 进入的二级页 — 旧原型把它们当一级入口了。

新版原型已全部纠正，并从 8 页扩到 **23 页**，覆盖 `app.json` 里注册的全部页面。

## 二、使用者视角：五类角色分别该怎么设计

这是本次优化的核心。逐角色拆解真实痛点，每一项都对应到具体实现。

### 2.1 买家（二手交易）——核心诉求是「信任」与「决策效率」

| 痛点 | 设计对策 | 实现位置 |
|------|---------|---------|
| 怕被骗，不敢当面交易 | **蓝 V 认证标识**贯穿列表→详情→卖家卡，并明确「已认证」文案 | `product-detail` 卖家卡 |
| 不知道价格是不是虚高 | 价格旁展示**原价划线 + 折扣对比** | 商品网格 `pcard-orig` |
| 拿不准成色 | 成色标签结构化（95新/可小刀/校内自提/当面验机） | 详情页 `dtag` |
| 找不到联系方式 | 底部固定 `私信` + `我想要` 双按钮，不滚动即可触达 | 详情 `actionbar` |
| 交易出风险 | **交易安全提示**（当面验货、拒绝提前转账）常驻详情页 | `notice warn` |

> 后端要点：`product-detail` 返回 `seller.campusVerified`，前端据此渲染 V 标；**不能**由前端自行判断认证状态。

### 2.2 卖家——诉求是「发得快」与「卖得掉」

| 痛点 | 设计对策 |
|------|---------|
| 填表项太多，发一半放弃 | **图片置首 + 4 个必填项**（图/名/价/描述），其余选填折叠 |
| 不知道该标多少钱 | 原价选填，自动算折扣；描述给结构化引导文案 |
| 成交率低 | 发布页直接提示「你是已认证用户，商品会自动带蓝 V，成交率更高」——**正向激励认证** |
| 卖完了还挂在列表里 | 「标记已售」状态流转，售出后从列表下架但保留详情 |

> 后端要点：`product-create` 对价格做 **NaN-safe 校验**（源码已实现，需保持）；`product-update` 支持 `sold` / `relite` 双向流转。

### 2.3 失主 / 拾获者——诉求是「尽快闭环」

这是校园最高频刚需，双向设计是关键：

- 寻物帖展示 **`私信联系` + `我捡到了`** 双按钮
- 招领帖展示 **`这是我的`** 单按钮
- 按**地点筛选**（宿舍区/教学楼/食堂），提升匹配率
- 「已找回」状态置灰并划线，**保留可见**（给其他用户信心，而非直接消失）

> 后端要点：复用 `posts` 集合，`kind = 'lost' | 'found'`；「已找回」复用 `resolved: true` 字段（源码中 `resolve` 云函数已支持），无需新增集合。

### 2.4 学生（泛用户）——诉求是「有用」与「有归属」

| 场景 | 设计对策 |
|------|---------|
| 新生不知道从哪看起 | **指南已核验标识**（`学工处 · 已核验`），把官方内容与 UGC 区分开 |
| 缺留存钩子 | **积分 + 连续签到**（连签 7 天额外 +20），积分可兑换改名卡 |
| 发的内容没人看 | **热门 tab**（近 7 天按点赞排序）+ 置顶徽章 |
| 任务帖过期后信息污染 | **过期归档**独立页 + 详情页「重新发布 / 标记已解决」 |

> 后端要点：`checkin` 需**幂等**（同一自然日重复调用不重复加分），源码 CHANGELOG 提到 v0.6.1 已修复，需保持并加测试。

### 2.5 管理员——诉求是「一眼看清待办」与「操作可追溯」

- 顶部三宫格直出**待审举报 / 待审认证 / 待审反馈**数量
- 分类管理支持**三级**（校区→版块→子版），纯运营动作无需改代码
- **审计日志**展示最近操作（谁、做了什么、原因），敏感操作留痕

> 后端要点：`admin` 云函数所有写操作必须 `checkAdmin` + 写 `admin_logs`；封禁/删除需**二次确认**。

### 3.2 建议改进项（按 ROI 排序）

#### 【高】限流复用业务计数，省一半 DB 读

当前 `rateLimit` 每次写操作都额外 `count()` 一次：

```js
// common-rate.js 现状（每次都多一次 count 读）
const res = await db.collection(collection)
  .where({ ...match, createdAt: db.command.gt(since) })
  .count()
```

**改造**：`post-create` 已经要查用户，可直接用 `users.lastPostAt` 字段做时间窗判断，省掉一次云数据库读。

```js
// 建议：在 users 文档上冗余 lastPostAt / lastProductAt
if (user.lastPostAt && Date.now() - new Date(user.lastPostAt).getTime() < 30000) {
  throw new AppError('操作过于频繁，请稍后再试', 'RATE_LIMITED')
}
// 发帖成功后顺带写入
await db.collection('users').doc(user._id).update({
  data: { postCount: _.inc(1), lastPostAt: new Date() }
})
```

> 收益：DB 读次数约 -15~25%（对应专家报告 C4）。注意：该字段需从 `getCurrentUser()` 的 `.field()` 白名单里放出来。

#### 【高】搜索从正则改为前缀匹配 + 分词

```js
// search/index.js 现状：正则匹配 title+content → 全表扫描
```

**改造**：数据量过万前，至少做到：① 关键词正则转义（源码已有）；② 加 20 字长度上限（已有）；③ 优先 `title` 前缀命中，仅当前缀无结果才扫 `content`。

```js
const safe = String(keyword).trim().slice(0, 20).replace(/[.*+?^${}()|[\]\\]/g, '\\$&')
// 第一轮：仅标题前缀（走索引）
let res = await db.collection('posts')
  .where({ status: 'normal', title: db.RegExp({ regexp: '^' + safe, options: 'i' }) })
  .limit(20).get()
// 第二轮兜底：标题+正文包含（全表扫，但只在第一轮为空时触发）
if (!res.data.length) { /* 原逻辑 */ }
```

#### 【中】通知未读数去掉高频轮询

改为**进入个人中心时刷新一次**，配合 `notification` 云函数的 `unread` action。源码已在 `notification` 提供 list/read/unread，确认 `notifications` 页面用的是 `onShow` 拉取而非 `setInterval`。

#### 【中】task-expire 已是惰性过期，cron 确认降频

`post-list/index.js:32-42` 已实现读侧惰性排除，`task-expire/config.json` 的 cron 应已从每小时降为每 6 小时。**建议在代码注释里写明这个约定**，否则后人可能误以为 cron 是主过滤器而删掉读侧逻辑。

#### 【中】图片压缩链路（已实现，需回归测试）

`utils/request.js:41` 的 `compressForUpload` 是 CDN 费用的关键闸门。建议补一条兜底：压缩后仍 > 1MB 时强制再压一轮。


## 四、2026 年的技术选型建议

结合当前生态，给几条务实的判断：

### 4.1 保持不动的

- **原生小程序 + TDesign**：项目已深度使用 TDesign，换框架（Taro/uni-app）的收益远小于迁移成本。原生在包体积和启动性能上仍有优势。
- **微信云开发**：单校场景（500~3000 人）月成本可控在 19.9~50 元，且省掉服务器运维。没有换自建后端的理由。

### 4.2 值得引入的

| 方向 | 方案 | 理由 |
|------|------|------|
| **AI 审核兜底** | 微信 `msgSecCheck` 之外，接一层**大模型内容分级**（如腾讯云内容安全 / 混元轻量模型） | `fail-closed` 会因接口超限误伤正常内容；二级审核可在宽松期降低误杀 |
| **AI 摘要** | 长帖自动生成一句话摘要，展示在瀑布流卡片 | 瀑布流卡片信息密度高，摘要能显著提升点击率 |
| **向量检索** | 帖子/商品嵌入向量，支持**语义搜索**（"想找个便宜的平板" → iPad） | 关键词搜索在二手场景明显不够用 |
| **订阅消息** | 评论/回复/关注变动推送 | 小程序唯一免费召回通道，专家报告列为 P1 |

### 4.3 明确不建议的

- **不要上 Web3 / 区块链存证**：校园社区无此需求，徒增复杂度。
- **不要过早做跨校联邦**：专家报告结论很明确——先做好单校，冷启动才是生死线。
- **不要接第三方支付**：iOS 端虚拟支付是审核红线，二手交易走线下当面交易反而更合规。

## 五、合规红线（必须优先于技术优化）

> 这是专家报告中的 **P0**，技术再优化也绕不过去。

| 红线 | 说明 | 应对 |
|------|------|------|
| **个人主体不能选「社区/论坛」类目** | 2026 年现行规则 | 挂靠校社团/校团委主体（成本≈0），或注册个体工商户 |
| 小程序名称含「社区/论坛/贴吧」会触发资质审查 | — | 改名如 `XX校园通` / `XX百事盒` |
| 必须完成 **ICP 备案** | 公众平台内提交，免费 | 上线前完成 |
| 个人主体**拿不到手机号授权** | — | 校园认证走学号人工审核（源码已如此实现，正确） |
| 免费环境**上线后第 15 天到期** | 到期不清数据 | 日历提醒 + 开自动续费 + 每周备份 |
