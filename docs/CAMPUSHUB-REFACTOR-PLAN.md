# CampusHub 对标大厂改造方案（v1）

> 目标不是"变成字节"，是把工程化水平拉到"优秀开源社区项目"的档次：能测试、能观察、能安全、能长大。
> 以下按 P0 / P1 / P2 排序，每层给选型、理由、明确的"不做什么"。

## 0. 总原则

- 对标的是**工程化水平**，不是规模技术。校园量级的微服务 / ES / K8s 是负资产，列入"别做清单"。
- 所有改造围绕一件事：让产品从"能跑的 demo"变成"可维护、可上线、可长大的产品"。
- 顺序理由：先服务层（一切的基础）→ 安全和可观测（上线底线）→ 形态扩展（流量主战场）→ 数据智能（增值）。

---

## 1. P0 —— 不做就永远是 demo

### 1.1 后端服务层（最核心）

- **现状**：业务逻辑全部焊在 Supabase（表、触发器、RPC），前端直连数据库。
- **选型**：NestJS + TypeScript + Prisma（ORM + 迁移）+ PostgreSQL（复用 schema.sql 的 17 表结构）
- **理由**：
  - 与现有前端全栈 TS，一套心智，可共享类型
  - 模块化（依赖注入）架构清晰，符合优秀项目标准
  - 单测生态成熟（Jest + Supertest）
  - 脱离 Supabase 平台绑定，逻辑可测、可扩展
- **备选**：Go(Gin) 高并发强但开发慢；FastAPI 适合纯后端团队，但放弃 TS 全栈统一
- **迁移范围**：`apps/web/src/api/*` 全部换成调自家 API；签到 / 计数触发器 / RLS 权限逻辑搬进服务层（数据库约束保留作兜底）
- **交付物**：REST + OpenAPI 文档、JWT 认证、统一错误码

### 1.2 测试与质量门禁

- **现状**：只有人工 QA 报告，零单测、零 E2E。
- **选型**：Vitest（服务层单测）+ Playwright（H5 E2E）+ CI 门禁（测试不过不能合 main）
- **目标**：核心服务单测覆盖率 ≥ 80%；5 条关键 E2E（登录 → 发帖 → 评论 → 审核 → 签到）
- **理由**：这是"优秀项目"与"demo"最本质的分界线。没有测试就没有重构的胆子。

### 1.3 内容安全

- **现状**：举报 + 人工审核，机审只留了占位。
- **选型**：腾讯云天御 / 阿里云内容安全 API（文本 + 图片，按量付费）→ 发布接口先审后发 + 现有举报闭环兜底
- **理由**：内容安全辅助手段。机审 API 约 100–300 元/月，比自建模型便宜一个数量级；校园量级以举报 + 人工审核闭环为主，机审列为可选扩展。

## 2. P1 —— 决定能不能长大

### 2.1 小程序端（主战场）

- **现状**：只有 H5，校园流量主战场缺失。
- **选型**：uni-app + Vue3（与现有技术栈同源，成本最低）；后端直接复用 P0 服务层
- **说明**：v1 因"拒绝微信依赖"弃了 uni-app；现在对标大厂回微信生态，工具选回 uni-app 是合理的——但教训是**后端不再依赖微信云开发**，小程序只是壳。
- **App 端**：暂不做。RN/Flutter 成本高，校园场景小程序 + H5 足够。

### 2.2 缓存与异步

- **现状**：无缓存、无队列，热点查询直接打库。
- **选型**：Redis（热点信息流 / 计数 / 登录态缓存）+ BullMQ（Redis Streams）做通知、计数、审核的异步化
- **理由**：并发兜底层。校园量级 Redis 单实例足够，别上 Kafka。

### 2.3 搜索升级

- **现状**：pg_trgm 模糊匹配。
- **选型**：Postgres 原生全文检索（tsvector + GIN）起步，中文分词用 zhparser；后续可加 pgvector 做向量召回
- **理由**：校园量级 FTS 足够，ES 集群是过度设计（见别做清单）。

### 2.4 可观测性

- **现状**：无日志、无监控、无告警，靠人肉看。
- **选型**：Sentry（前端 + 服务端异常）+ pino 结构化日志 + UptimeRobot 探活告警；Prometheus + Grafana 列为可选项
- **理由**：先保证"出事能知道、能定位"，指标大盘是第二步。

---

## 3. P2 —— 数据智能（与你的专业强相关）

### 3.1 埋点与数据仓库

- **现状**：零埋点。
- **选型**：自研轻量埋点 SDK（前端事件上报：曝光 / 点击 / 发布 / 搜索）+ 事件表（Postgres 起步，量大迁 ClickHouse / Doris）
- **理由**：埋点是推荐、运营、AB 的地基。先自研省成本，跑通再上神策类平台。

### 3.2 个性化推荐

- **现状**："推荐"是点赞排序，假推荐。
- **选型**：基线推荐（热门 + 新帖加权，SQL 实现）→ 协同过滤（用户行为矩阵，Python 离线脚本，正好用你的大数据技能）→ 向量召回（pgvector）
- **理由**：推荐不是一上来就上大模型，先做"有依据的排序"，再用数据迭代。

### 3.3 后台规范化

- **现状**：9 个模块散在 vue-pure-admin 模板里。
- **选型**：保留模板框架，抽出统一 CRUD 规范（列表 / 审核 / 表单三件套组件），沉淀成自己的后台基础
- **理由**：后台是运营工具，规范比炫技重要。

## 4. 实施顺序（里程碑）

| 里程碑 | 内容 | 周期（单人） | 验收标准 |
|---|---|---|---|
| M0 | 接口清单 + schema 评审 + 测试策略 | 1 周 | 改造范围冻结 |
| M1 | NestJS 服务层 + auth + 核心 API + 单测 | 3–4 周 | 学生端全功能跑在自家后端 |
| M1+ | 工程债 12 项 + admin 迁移 + pino 结构化日志 + CI 门禁 | 2 周 | 可观测 + 自动化门禁就绪 |
| 可选 | 机审 / Sentry / Redis+异步 / FTS / 小程序 / 推荐 | 按需 | 非承诺，按量接入 |

**总工期**：单人约 3–4 个月全职；双人可压到 2 个月。

| **合计** | **几百元/年**，仍远低于自建全套机房 |

## 6. 别做清单（重要）

以下"大厂标配"对校园量级是负资产，写上等于装：

- 微服务拆分 / K8s / 服务网格 —— 单机能跑完的业务，拆了只剩运维负担
- 分库分表 —— 数据量差 3 个数量级
- ElasticSearch 集群 —— pgvector / FTS 起步够用
- 自建推荐平台 / 特征平台 —— 基线推荐用 SQL + 离线脚本就能做
- Kafka / 大数据全家桶 —— 队列用 Redis Streams 就够
- 自研 IM —— 接开源方案（OpenIM / 环信）
- 全面微前端 —— 两个端不需要

---

## 7. 结论

- **核心路线已全部完成**：服务层 / 核心单测 / 管理后台迁移 / pino 结构化日志 / CI 门禁——campushub 是可上线、可复用的开源产品。
- **可选扩展**：机审 / Sentry / Redis+异步 / FTS / 小程序 / 推荐，按需接入，非本项目承诺。
- **P2 数据侧是增值点**：也是大数据专业能写进简历和论文的部分。

**顺序本身就是工程纪律：核心闭环完成之前，不碰可选扩展。**

**方案外新增工程化改造**（修债清单 12 项，均完成）：会话双 token 续期、mock 双轨收拢、图片压缩上传、请求缓存/超时、usePagination、路由 history、骨架屏/暗黑/动效、openapi 类型闭环。

**接口清单调整**（M0 v1 → 实际落地 v2）：
- 互动端点资源化：`POST /interactions/like {targetType,targetId}` → `/posts/:id/like`、`/products/:id/collect` 等
- 查询类端点归位：`GET /interactions/liked|collected` → `/me/likes`、`/me/collects`、`/interactions/status`
- 我的帖子/商品：`/users/me/posts` → `/posts/me`、`/products/me`（资源控制器下更 REST）
- 搜索合并：`/search/posts`、`/search/products` → 统一 `/search?q=`
- 编辑资料：`PATCH /users/me` → `PATCH /auth/me`
- **admin 模块已实现（28 端点）**——M1+ 追加完成：真 AdminGuard（401/403/封禁）、全写操作审计落 `admin_logs`；前端 `apps/admin` 已对接新服务层
